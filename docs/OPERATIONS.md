# Governed dance-studio operations

The launcher does not install, migrate, seed, create databases, or kill port owners. Bootstrap, configure `.env`, migrate, provision tenant roles, then start. Demo seeding is separately guarded.

The governed operations boundary models encrypted guardian/student references, purpose-specific consent with policy versions and evidence hashes, capacity and ordered waitlists, schedule conflict checks, exact-cent proration/refunds, idempotent attendance and ledger entries, payment reconciliation, tenant roles, optimistic transitions, provider-sync failures and audit events. Minor enrollment requires current guardian participation consent. Photo/video publication requires separate current media consent. A drop cannot complete without a versioned ledger adjustment, and program completion requires reconciled attendance. Generated gap endpoints and startup DDL are disabled.

Scheduling, payments/accounting, messaging, access/attendance and media adapters remain disabled pending credentials, webhook-signature validation, contract/replay fixtures and provider failure tests. The service must receive tokenized payment references only; it must never receive card data. Child-safety, guardian authority, emergency/medical handling, background-check policy, music/performance licensing, refund terms and media release language require studio counsel and qualified operators before launch.

## Guardian family read view

Run `scripts/migrate.sh` to apply `002_guardian_family_read.sql`, `003_guardian_enrollment_requests.sql`, and `004_direct_enrollment_request_hash.sql` after the base schema and governed operations migration. A parent account can open `/guardian` to read its linked children's governed enrollments and latest attendance for each studio. The API is `GET /api/guardian/studios` and `GET /api/guardian/studios/:tenantId/family`; the server derives the user from a signed token and checks the current account role plus active account and child links on every read. It returns external child references, class/status information and attendance only; encrypted names, birth dates, medical data, payments and messages are excluded. The older email-linked `/api/portal` routes are behind the staff boundary and are not used by the guardian view.

An authorized studio operator must establish both a `dance_guardian_accounts` row for the parent user and a `dance_guardian_student_links` row for each child, with `linked_by` set to that operator's user ID. These links are not inferred from matching email addresses or participation consent. Record the operator's identity and basis for the linkage in the studio's approved verification process before inserting them; this code does not verify guardian identity or legal authority. Revoke access by setting `revoked_at` and `revoked_by` on either link. A self-registered parent has no family visibility until these links are provisioned.

## Guardian enrollment requests

The same parent page lists currently open class sections and lets a guardian request a class for an actively linked child. Minor requests require current program participation consent. `POST /api/guardian/studios/:tenantId/enrollment-requests` requires a stable `Idempotency-Key` for retry; duplicate pending child/class requests and cross-studio records are rejected. The guardian can cancel a pending request, and a revoked child link removes it from their view. A request does not reserve a place, enroll a child, charge a card, or create a payment record.

Registrars and managers review requests in `/governed-operations`. Acceptance requires an explicit age/skill suitability attestation; the server rechecks guardian access, child link, consent, class term, schedule and capacity under a transaction. It records an active, waitlisted or blocked governed enrollment with calculated tuition and audit evidence, and labels payment unverified. Declines require a reason. The guardian sees the decision and resulting enrollment. Class recurrence, verified age/skill data, guardian legal authority, actual payment provider receipts, tuition invoicing and messaging remain external acceptance work. The studio must not treat an accepted request as a paid or externally confirmed booking.

Direct staff enrollment through `POST /api/governed-operations/enrollments` remains available to active registrars, managers and admins. It shares the child placement lock with guardian-request review, uses a stable 8–128 character idempotency key and stores a SHA-256 fingerprint of the actor, child, class, guardian and enrollment date. An exact retry returns the existing enrollment; reusing the key with different inputs is rejected. Older direct-enrollment records without a fingerprint cannot be replayed as exact requests and require a new key. A direct placement still records tuition as an internal amount; no provider payment is verified.
